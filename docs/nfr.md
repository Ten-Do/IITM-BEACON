# Non-Functional Requirements (Quality Attribute Scenarios)

> **Locked — approved baseline (2026-09-10).** Reviewed for consistency across `scope.md`,
> `use-cases.md`, and `nfr.md`. AI agents: do not edit this file — wording, structure, or
> cross-references — without the user's explicit approval first.

Each NFR below is written as a 6-part Quality Attribute Scenario: **Source** (who/what
triggers it) → **Stimulus** (the triggering event) → **Environment** (conditions it happens
under) → **Artifact** (the part of the system affected) → **Response** (what the system does)
→ **Response Measure** (how it's judged met).

IDs are stable, descriptive slugs, not sequence numbers — one can be removed or added without
forcing a renumbering pass across every file that cites one.

## NFR-GALLERY-PERFORMANCE: Gallery load performance
- **Source:** Visitor
- **Stimulus:** requests the gallery's first page
- **Environment:** normal operation, production-sized dataset (hundreds of approved
  testimonials)
- **Artifact:** gallery listing endpoint/page
- **Response:** system returns the rendered page
- **Response Measure:** within 2 seconds, 95th percentile

## NFR-SEARCH-PERFORMANCE: Filter & search responsiveness
- **Source:** Visitor
- **Stimulus:** applies a country filter, a topic-group-or-standalone-topic filter, and/or a
  free-text search query, in any combination
- **Environment:** normal operation, production-sized dataset
- **Artifact:** gallery filter/search query (indexed on `status` + `country_code` on
  `Testimonial`, and on `topic_id` on `TestimonialSection` — a group filter expands to its
  member topic_ids; `ILIKE` on section text/name)
- **Response:** filtered/searched results returned
- **Response Measure:** within 1 second, 95th percentile

## NFR-MODERATION-QUEUE-PERFORMANCE: Moderation queue load performance
- **Source:** Admin
- **Stimulus:** opens the pending-testimonials queue (UC-VIEW-PENDING-QUEUE)
- **Environment:** normal operation, production-sized dataset (potentially dozens of pending
  testimonials awaiting review at once)
- **Artifact:** moderation queue listing endpoint/page
- **Response:** system returns a paginated page of pending testimonials, full article view per
  item
- **Response Measure:** within 2 seconds, 95th percentile, regardless of total pending count

## NFR-DASHBOARD-PERFORMANCE: Homepage dashboard load performance
- **Source:** Visitor
- **Stimulus:** opens the homepage (UC-VIEW-DASHBOARD)
- **Environment:** normal operation, production-sized dataset (hundreds of approved
  testimonials)
- **Artifact:** dashboard aggregate queries (country map, achievement/score stat cards,
  per-topic-group testimonial counts)
- **Response:** system returns the rendered dashboard
- **Response Measure:** within 2 seconds, 95th percentile

## NFR-ADMIN-OTP-BRUTEFORCE: Admin OTP brute-force resistance
- **Source:** an unauthenticated attacker
- **Stimulus:** repeatedly submits guessed OTP codes against the verify endpoint within one
  OTP's validity window, or repeatedly requests fresh OTPs against the request endpoint
- **Environment:** normal operation, internet-facing admin login endpoint
- **Artifact:** admin-auth OTP request/verify endpoints / `OtpService`
- **Response:** see UC-ADMIN-OTP-VERIFY's alternate flow for the verify-side lockout mechanism
  (attempt counter, OTP invalidation); the request endpoint is separately rate-limited so it
  can't be used to spam OTPs or as a slower brute-force vector; this NFR fixes the numeric
  bounds both must satisfy
- **Response Measure:** no more than the configured max attempts (default proposed: 5) are
  accepted per issued OTP; OTP time-to-live is configurable (default proposed: 5 minutes); OTP
  *requests* are capped to a configurable rate per email (default proposed: 1 per minute) — all
  enforced server-side

## NFR-CONTACT-CONFIDENTIALITY: Contact-method confidentiality at rest
- **Source:** someone with read access to the database or its storage/backups, but not through
  the running application (e.g. a stolen backup, a compromised low-privilege DB credential)
- **Stimulus:** attempts to read a contact-method value (including the login email) directly
  from storage
- **Environment:** any environment (dev/test/prod) where the DB or a backup of it could be
  accessed outside the running application
- **Artifact:** stored contact-method values — one per submitter-added entry, plus the login
  email
- **Response:** each value is stored as ciphertext (application-level encryption via a JPA
  attribute converter), unreadable without the application's encryption key. Decrypting inside
  the running application is fine whenever a feature legitimately needs it — the constraint is
  on exposure, not on decryption itself: no single request returns contact-method values for
  testimonials beyond the ones that request is already, legitimately operating on.
- **Response Measure:** no contact-method value is ever persisted or logged in plaintext; no
  endpoint or query anywhere in the system returns decrypted contact-method values in bulk
  across testimonials outside its own legitimate scope (e.g. no full-table or
  cross-testimonial export exists)

## NFR-UPLOAD-SPOOFING: Upload content-spoofing resistance
- **Source:** Visitor (possibly malicious)
- **Stimulus:** uploads a file with a spoofed `Content-Type` header (e.g. an executable renamed
  to look like a JPEG)
- **Environment:** the submission endpoint, any environment
- **Artifact:** submission-flow validation logic (file content inspection)
- **Response:** validation inspects the actual file content, never the client-declared
  `Content-Type`; a mismatch is rejected the same way as any other invalid upload
  (UC-CREATE-TESTIMONIAL/UC-EDIT-TESTIMONIAL's alternate flow — nothing persisted, actionable
  message returned)
- **Response Measure:** zero non-image files are ever written to the uploads volume, regardless
  of the declared `Content-Type`

## NFR-ERROR-TRANSPARENCY: Error transparency without leakage
- **Source:** Visitor or Admin
- **Stimulus:** sends a request that fails (validation error, auth failure, not-found,
  unexpected exception)
- **Environment:** any environment, especially production
- **Artifact:** centralized error handling (`@RestControllerAdvice`)
- **Response:** the client receives a consistent error response with an appropriate HTTP status
  and an actionable message
- **Response Measure:** 0% of error responses contain a stack trace or internal exception
  detail; 100% map to one of the defined HTTP status codes

## NFR-CATALOG-CONFIGURABILITY: Topic/achievement content configurability
- **Source:** Admin, via the catalog screen (UC-MANAGE-TOPIC-GROUPS, UC-MANAGE-TOPICS,
  UC-MANAGE-ACHIEVEMENTS)
- **Stimulus:** adds, renames, reorders, deactivates, deletes, or (topics only) re-parents a
  `Topic`, `TopicGroup`, or `Achievement` row
- **Environment:** any environment, no application redeploy involved
- **Artifact:** `Topic`, `TopicGroup`, and `Achievement` reference tables
- **Response:** the change is reflected on the live submission form and gallery filters, and —
  for a deactivation or delete — in the gallery articles, moderation queue and edit forms of
  testimonials that already reference the entry (decision 28)
- **Response Measure:** takes effect immediately — these tables are read per request, with no
  application-level caching to invalidate, so no code change or redeploy is ever required

## NFR-VISITOR-OTP-BRUTEFORCE: Visitor login-OTP brute-force and enumeration resistance
- **Source:** an unauthenticated attacker
- **Stimulus:** repeatedly submits guessed OTP codes against the visitor verify endpoint within
  one OTP's validity window, repeatedly requests fresh OTPs for the same or many emails, or
  probes the request endpoint to learn which emails have a testimonial
- **Environment:** normal operation, internet-facing visitor login endpoint (UC-VISITOR-LOGIN);
  unlike the admin's single in-memory OTP (decision 6, valid only because there is exactly one
  admin), this endpoint must hold many visitors' OTP state at once, correctly and concurrently
- **Artifact:** visitor login OTP request/verify endpoints
- **Response:** see UC-VISITOR-LOGIN's alternate flow for both the lockout mechanism and the
  identical-response handling on the request step; the request endpoint is separately
  rate-limited per email (and per IP, to blunt spraying across many emails) so it can't be used
  to spam OTPs or as a slower brute-force vector; this NFR fixes the bounds they must satisfy
- **Response Measure:** same numeric bounds as NFR-ADMIN-OTP-BRUTEFORCE (max attempts, TTL, and
  request rate); additionally, two OTP requests for different emails (one with an existing
  testimonial, one without) must be indistinguishable from the response alone
