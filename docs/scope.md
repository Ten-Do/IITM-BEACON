# Scope

> **Locked — approved baseline (2026-09-10).** Reviewed for consistency across `scope.md`,
> `use-cases.md`, and `nfr.md`. AI agents: do not edit this file — wording, structure, or
> cross-references — without the user's explicit approval first.

## Goal

Build a single platform for collecting and browsing exchange-student testimonials about
studying at IITM — turning the exchange experience from an opaque, intimidating black box into
something a prospective student can transparently see into before choosing it.

## Explicitly not a goal

General informational content about exchange life (beyond what a personal testimonial covers)
is out of scope for this gallery — see "Out of scope" below.

## In scope (MVP)

- Public gallery: browse / filter by country / filter by topic group or standalone topic /
  free-text search / paginate approved testimonials.
- A testimonial renders as an article: a set of guided, optional topic sections (each with its
  own text and photos), a required 0–10 recommendation score, and a set of achievement
  checkboxes.
- Photos are attached per topic section (not to the testimonial as a whole), each carrying an
  automatic tag from its section's topic plus up to 10 free-form custom tags. Photo count per
  testimonial and max size per photo are both enforced server-side and configurable via env
  vars — no fixed numbers are asserted in this documentation.
- Achievement checklist: a fixed set of boolean checkboxes (e.g. "made new friends here"),
  shown in full near the end of the submission form (after the contacts block, before the
  consent checkbox).
- Topics are organized in two levels — a small set of top-level groups (e.g. "OGE"), each
  holding several subtopics (e.g. "Support", "Gaps", "Emergencies") — plus a handful of
  standalone, ungrouped topics. Achievements stay a flat list. Both are database-driven
  reference data, requiring no code change or redeploy to add/rename/reorder/deactivate an
  entry.
- Admin catalog screen: a dedicated admin UI for creating, renaming, reordering, deactivating,
  deleting, and re-parenting topic groups and topics (moving a topic between groups, or
  promoting it to standalone), and for creating, renaming, reordering, deactivating, and
  deleting achievements. Deactivating hides the entry's content in existing testimonials too,
  reversibly; deleting removes that content for good.
- Contact methods: a submitter may list 0–N ways to reach them (email, WhatsApp, Telegram,
  Instagram, Twitter/X, ...), each given as a number, handle, or link, whichever is convenient,
  and validated against the accepted formats of its type from a database-driven contact-type
  list, same pattern as topics/achievements. Each entry is independently marked public or
  private by the submitter.
- On-demand contact reveal: no contact method is shown by default, even on an approved
  testimonial — a visitor must explicitly request it, which triggers a separate lookup
  returning only the entries the submitter marked public, rather than being included in the
  normal browse/detail response.
- Self-service submission and editing: a visitor writes or edits a testimonial only after
  logging in with an email OTP. The system then checks whether a testimonial already exists for
  that email — first-timers get a blank form, returning submitters get their existing
  testimonial pre-filled and fully editable. Editing a testimonial that was `PENDING` or
  `REJECTED` always resets status to `PENDING`. Editing an `APPROVED` testimonial resets status
  to `PENDING` only if the change touches section text, photos, or identity fields; a change
  limited to country, recommendation score, achievements, or contact methods applies
  immediately, without re-entering moderation. Either way, content changed since the last
  approval is flagged for the admin wherever moderation does happen, and shown as "updated"
  publicly once re-approved.
- Submission form: mandatory identity fields (first name, last name, roll number, admission
  year — email comes from login); country; the recommendation score; one or more top-level
  entries picked from the topic catalog — picking a topic group reveals all of its subtopics as
  input blocks (each still individually optional), picking a standalone topic reveals just
  itself, so the visitor never sees the full topic list expanded at once; at least one subtopic
  or standalone topic must actually be filled in (picking a group alone doesn't count); the
  optional contacts block; the achievement checklist; one mandatory data-processing consent
  checkbox.
- Single admin account, passwordless OTP login.
- Moderation: pending queue (full article view including contact info, so the admin can judge
  it; fields changed by a resubmitted edit are flagged), approve/reject one at a time (reject
  can optionally include a reason, emailed to the submitter so they know to log in and fix it),
  30-day retention on rejected testimonials before hard delete.
- Homepage analytics dashboard: a map highlighting countries with testimonials, plus numeric
  stat cards over achievements, recommendation scores, and testimonial counts per topic
  group/standalone topic.
- Every contact method's value, including the login email, is encrypted at rest at the
  application level. Identity fields (name, roll number, admission year) are plain text,
  visible to the admin only — same treatment as today's full name — except that a derived
  "first name + last initial" label (e.g. "David J.") is shown publicly, but only inside a
  testimonial's already-open expanded article, never on gallery cards/list views. Nothing else
  is specially encrypted (see `decisions.md`).

## Out of scope (for now)

- Multi-admin management — single seeded admin only.
- General informational content beyond personal testimonials (see "Explicitly not a goal").
- Automated verification of identity fields (roll number, admission year) against a real IITM
  student registry — not planned; moderation relies on the admin's manual judgment.

## Future direction (not MVP, but shapes the architecture)

A future integration with a separate, independently-developed sibling service (same tech
stack) is anticipated, targeting a single unified application. Consequence for architecture:
keep `adminauth` and `common` self-contained and reusable now, rather than coupling them to
gallery-specific assumptions.

## Actors

- **Visitor** — no login. Browses the public gallery.
- **Authenticated Visitor** — a Visitor who logged in with an email OTP (required only to write
  or edit a testimonial, never to browse). Same rights as Visitor, plus: submit a new
  testimonial, or fully edit their own existing one. Becomes a data subject once they submit —
  see Constraints.
- **Admin** — single account. Reviews and moderates submissions, and manages the topic and
  achievement catalog, via passwordless OTP login.
- **Scheduler** — system-initiated, no human operator. Runs the weekly job that hard-deletes
  long-rejected testimonials.

## Constraints

### Budget

No dedicated budget. Free-tier hosting is the default assumption, but hosting on university
servers is a real, available option — not purely a solo/free-tier deployment forever.

### Technical

- Java (fixed language), Maven, Spring Boot (Spring Web, Spring Data JPA, Thymeleaf),
  MultipartFile for uploads.
- H2 for dev/test, PostgreSQL for prod.
- Must run containerized: Dockerfile + docker-compose (app + Postgres).

### Time

- Design doc: 11 Sep 2026.
- Mid-demo: 9 Oct 2026.
- Final submission: 6 Nov 2026.
  No additional external deadline identified beyond these.

### Legal / data protection

- Data may only be stored if the submitter has explicitly agreed to a personal-data-processing
  policy — a mandatory consent checkbox at submission time. Personal data collected: first
  name, last name, roll number, admission year, login email, and 0–N optional contact methods.
- Each contact method's value, including the login email, is encrypted at rest at the
  application level, and is only ever decrypted on an explicit, separate request (OTP dispatch,
  a visitor revealing a submitter's public contacts, or the admin's moderation queue) — never
  bundled into the normal public-facing testimonial read path. Other fields are not specially
  encrypted, so free-text search keeps working directly against the database.
